The core idea: one engine, several personalities
Don't build four apps. Build one participant runtime (SimHost) that is entirely config-driven, and give it four personality packs. A "REG app" then becomes a folder of configuration + BOD handlers + seed data, not a codebase. Adding CONSTRUCT, ENG, or MMS later costs a config file, not a project.

Phase 0 is a prerequisite: extract IsbmRestClient, SessionHelper.OpenAndConfirmAsync, and the session store out of CIR/CirProvider/Infrastructure/ into Oiie.Isbm.Client. Every participant must use the tested client. Hand-rolling HTTP in the simulator is how you end up debugging channelUri vs uri again in seven places.

REG-ASSET is the one to build first after REG-LOCATION — it's the only participant that exercises request/response and publish/subscribe and BOD confirmation in a single flow.

Every participant registers its own objects into ws-CIR on write (Category = Segment / Asset / Model / Material, SourceID = participant ID, SourceOwnerID = org), and resolves foreign identifiers through GetRegistry / GetEquivalentEntries on read. That's what makes the demo about CIR rather than incidentally using it.

The choreographies
Each is a YAML file: participants, channel/topic setup, ordered steps, and assertions.

A — Information handover (UC1). ENG publishes SyncSegments. REG-LOCATION ingests, registers entries in CIR, republishes on the O&M channel. MMS receives, sees an unknown SourceID, calls CIR, gets the CIRID cluster, maps to its own tag. Proves: pub/sub fan-out + CIR as the identity bridge.

B — Asset install (UC5). CONSTRUCT posts ProcessAssetSegmentEvent on a request channel. REG-ASSET reads it, applies, posts AcknowledgeAssetSegmentEvent as the response, then publishes SyncAssetSegmentEvent to O&M. Proves: request/response, response correlation on sessions/{id}/requests/{requestMessageId}/response, confirmation semantics, and the pub/sub follow-on.

C — Product data pull (UC4). REG-MATERIAL issues GetModels with a filter; REG-PRODUCT answers ShowModels. Then REG-PRODUCT publishes an engineering change advisory that REG-MATERIAL and MMS both consume (scenarios 25/26).

D — Identity reconciliation. ENG and CONSTRUCT both describe the same physical tag under different IDs. Operator uses the control tower to merge; the sandbox issues ChangeEntryCIRID; MMS re-resolves and now sees one object. This is the scenario that justifies CIR's existence to a non-technical audience.

E — Cold bootstrap via Service Directory. A new participant starts knowing only the Service Directory endpoint. It sends GetIsbmService, receives ShowIsbmService, self-configures endpoint/channel/topic/token, and joins scenario A mid-flight. This is your acceptance test for the Service Directory work that's next up, and it's the most persuasive demo in the set.

F — Negative paths. Expired publications, sessions abandoned and recovered, filter that matches nothing, schema-invalid BOD rejected with a fault, duplicate delivery. Also: give participants a real NotifyListener endpoint — the sandbox is the natural vehicle to close the three ISBM conformance skips.

How this becomes a test suite, not just a demo
Two run modes over identical code:

--mode ci — headless, seeded deterministic IDs, injected clock, exits non-zero on assertion failure. Lives in Sandbox/Testing/Ecosystem.Tests, runs against the deployed Azure ISBM/CIR endpoints or a local pair.
--mode demo — Blazor UI, manual stepping, pause-on-step.
Assertion vocabulary in the scenario files:

yaml
- assert: message_received
  at: mms
  channel: /Enterprise/Site/OandM
  bod: SyncSegments
  within: 30s
- assert: bod_valid          # XSD validation, not just well-formed
- assert: store_contains
  at: reg-asset
  query: "AssetSegmentEvent where AssetId='P-101-A' and Type='Install'"
- assert: cir_equivalent
  entries: ["ENG:TIC-106", "REG-LOCATION:234443", "MMS:UNIT101.TOP_TEMP"]
Correlation is the piece that makes debugging tractable. Generate a scenario GUID, carry it in the BOD ApplicationArea/BODID and in an ISBM message topic or property, and stamp it as a custom dimension on every App Insights event from every participant plus the ISBM and CIR providers. One KQL query then reconstructs the entire multi-hop exchange as a single timeline — which is also, incidentally, exactly the artifact you want to show a customer.

The web UI
Per-participant page: identity card (SourceID, SourceOwnerID, ISBM endpoint, channels/topics/session state), a grid of the objects it owns, an inbox/outbox with raw BOD XML and a green/red schema-validation badge, and buttons for the actions this participant can initiate ("Publish as-built segment", "Request models matching…").

Control tower page: live swimlane of messages crossing participants, the channel topology, and a CIR equivalence explorer showing CIRID clusters spanning sources. This is the single screen that answers "does the ecosystem work?" without anyone reading XML.

Scenario runner: pick a choreography, step or run, watch assertions turn green.

Deployment: one Azure Container App or App Service running all personalities as configured tenants, not seven Function Apps. Keeps cost and provisioning noise down, and provision.ps1 can carry the ISBM/CIR settings forward the way it already does.

The open dependency
The project files give us the ws-CIR BOD schemas and Meta.xsd, but not the CCOM 4.x BOD schemas for the REG nouns — SyncSegments, ShowAssets, ProcessAssetSegmentEvent, ShowModels and friends. Without those, participants can exchange structurally plausible XML but the bod_valid assertion has nothing to validate against, and given the defect history in both the ws-CIR package and the Service Directory PDF, inferring those shapes is exactly the kind of guessing that has cost time before.

Do you have the CCOM BOD schema package (or a MIMOSA reference implementation of it) available? If yes, phase 1 can validate from day one. If not, I'd scope phases 1–2 to the BODs we hold schemas for and treat CCOM payloads as opaque-but-shaped until the package lands.
