# Handoff — 2026-09-06

## Where it stands

SC01 has now been run end to end against deployed dev apps, by hand, for the
first time. Every leg named as untested in
[hand-off-2026-09-01.md](hand-off-2026-09-01.md) has been exercised at least
once with a real element: create in ENG, promote to a named version, drain
onto ISBM, drain into REG-LOCATION as a `Proposed` tag, and confirm it in the
stewardship queue. A correction to an already-promoted element was also
exercised and correctly overwrote the existing proposed row instead of being
dropped as a duplicate (the SC01 correction path from the 2026-09-01 session's
follow-on work).

Four elements were promoted across the session (`CAN-01` through `CAN-04`,
named versions `A` through `D+`), and all four ended up correctly represented
in `GET /admin/reg-location/stewardship`. One promotion was also edited after
promotion and the correction reached REG-LOCATION as expected.

## What was actually broken, and what was just slow

Two distinct things were confused with each other before this session, and are
now separated:

1. **`EngEngine__Enabled` was `false` on `acme-engn-eng-dev`.** This gates the
   *outbound* SyncSites/marker publication and genuinely needs
   `IModelId`/`ITwinFederationId` resolved first, per the existing README
   guidance. Corrected earlier in this session by setting it `true` and
   re-running the iTwin bootstrap.
2. **`RegLocationEngine__IngestEnabled` was `false` on
   `acme-engn-reglocation-dev`.** This is the actual bug, and it is new: see
   DR-025. It gates the *inbound* leg — the one that reads ENG's already
   published segments off ISBM — which needs nothing iTwin-specific to exist
   first. It had been grouped with `Enabled` under the same "wait for a
   federation id" reasoning, which does not apply to it. With it `false`, the
   timer fired every two minutes, returned immediately, and logged nothing,
   so the queue looked stuck with no error anywhere to explain why.

Once both flags were corrected and the ingest schedule was tightened from
`0 */2 * * * *` to `*/10 * * * * *`, a promotion in the ENG UI reached the
REG-LOCATION stewardship queue in well under 20 seconds without any manual
drain call — confirmed live with `CAN-04`.

**Fixed in code/config this session** (not just live app settings — the
defaults themselves were wrong):

- `deploy/engines/deploy-engine.ps1` — `IngestEnabled` default flipped to
  `'true'`; `RegLocationEngineIngestSchedule` default changed to
  `*/10 * * * * *`.
- `RegLocationEngine/local.settings.json` — same two changes, so a fresh local
  clone behaves the same way as the corrected deployed app.
- `deploy/engines/README.md` — the "Settings the script does not decide"
  section rewritten to stop conflating `Enabled` and `IngestEnabled`, and to
  say plainly what happens if `IngestEnabled` is ever reset to `false`.
- `docs/decision-register.md` — DR-025 records the reasoning and the fix.
- `docs/open-items.md` — new entry: `acme-engn-reglocation-dev` (and possibly
  the other three engine apps) has no Application Insights telemetry at all,
  which is why this took manual `GET engine/status` / `POST engine/ingest`
  probing to find rather than a log query.

**Not yet corrected in already-deployed environments other than
`acme-engn-reglocation-dev` dev**, since only that one app's live settings were
touched directly. Any other environment stood up from the old script defaults
still needs:

```powershell
az functionapp config appsettings set -g <rg> -n acme-engn-reglocation-dev `
    --settings RegLocationEngine__IngestEnabled=true `
               RegLocationEngineIngestSchedule="*/10 * * * * *"
```

## Verified this session (live, against `acme-*-dev`)

- `GET /admin/reg-location/stewardship?twin=<guid>` on `acme-api-sandbox-dev`
  returns all four promoted elements with correct `Proposed` state, correct
  `sourceIdentifier`/`proposedName`, and correct `assertedContext`.
- `EngEngine`'s marker drain (`GET/POST engine/status`, `engine/drain`) tracks
  `publishedMarkers` monotonically as new named versions are created — no gap
  there once `Enabled=true`.
- `RegLocationEngine`'s ingest drain (`POST engine/ingest`) reports
  `tagsProposed: 1` for each new segment and `alreadyKnown` (not
  `tagsProposed`) for a redelivered one, matching the idempotency design from
  DR-021 and the 2026-09-01 correction fix.
- A correction to an already-promoted ENG element reached REG-LOCATION and
  overwrote the existing proposed row rather than being ignored.
- The local React UI (`WorkflowOrchestration`, `npm run dev`, proxying
  `/admin` to `acme-api-sandbox-dev`) reflects all of the above once
  hard-refreshed. One session artifact worth noting for whoever tests next:
  restarting the Vite dev server resets `activeTwin` to `null` client-side:
  re-select the twin (or hard-refresh after the picker repopulates) before
  concluding data is missing.

## Tried and rejected this session

- **Assuming the empty queue was a REG-LOCATION scoping bug again** (the
  2026-09-05 fix). Ruled out quickly: `GET tags/proposed` on
  `acme-api-reglocation-dev` directly showed the tag existed with the correct
  `scopeId`, which meant the gap was upstream of the provider, not in how the
  sandbox read it.
- **Assuming the gap was ENG-side (marker never published).** Ruled out via
  `GET engine/status` on `acme-engn-eng-dev` — `publishedMarkers` incremented
  correctly for every new named version, including the one that was missing
  downstream, which pointed the search at `RegLocationEngine` instead.
