ENG publishes federation identity on the wire correctly, the Blazor UI is gone,
and `RegLocationEngine` now exists as the **outbound** leg of SC01. The solution
builds clean and `Oiie.Sandbox.Tests` passes 114 tests (104 previous + 10 new).

SC01 still does **not** run end to end. See "the one thing missing" below.

Committed and settled:

  `Segment.UUID` carries the element's FederationGuid, `InfoSource/UUID` carries

- `EngProvider/` — ENG's REST surface over the ECSchema design store. Elements,

- `RegLocationProvider/` — REST provider over an EIS-derived SQL schema. Tags,

  `GET tags/proposed`, and a thin `IApprovalNotifier` seam.
- `RegLocationEngine/` — new. Receives the approval, reads the tag back,

## The intended SC01 flow, and where the code actually is

Elements originate in external tools; in this emulation they are created by hand
in ENG. A NamedVersion releases them, they are wrapped as `SyncSegments`, they
reach REG-LOCATION as **proposed** tags, a steward approves, and the approved
location continues its journey.

| Leg | Status |
|---|---|
| Create elements in ENG | done (`EngProvider`, by hand) |
| NamedVersion → `SyncSegments` → ISBM | done (`EngEngine`), but **polled, not event-driven** |
| ISBM → REG-LOCATION as `Proposed` tags | **missing — nothing implements this** |
| Steward approves in REG-LOCATION | done (`POST tags/{tagId}/approve`) |
| Approval → ISBM + CIR | done (`RegLocationEngine`) |

Two caveats on the "done" rows that a reader should not have to discover:

- **The NamedVersion is detected by polling, not by an event.** `EngEngine` runs
  on a timer with a watermark plus an overlap window. Deliberate: a missed event
  is missed forever, whereas a watermark that is behind catches up. The same
  reasoning produced `SweepAsync` on the REG-LOCATION side.
- **`CreateTagRequest.State` still defaults to `Approved`.** Chosen so the
  existing bootstrap seed and every current caller kept working unchanged. Under
  the intended flow a tag arriving from ENG must land as `Proposed`, so the
  inbound consumer must pass it explicitly. That makes the safe behaviour depend
  on a caller remembering — the default should probably be inverted, with the
  seed saying `Approved` out loud. Not done; flagged in `open-items.md`.

## Tried and rejected
- **Putting the stewardship gate in the engine.** The first reading of "release
  segments on tag approval" put the hold in `RegLocationEngine`. Wrong: approvals
  would then only count while the integration was running, making the customer's
  own governance a property of somebody else's middleware. The gate is a state
  transition in the provider; the engine reacts afterwards. See DR-020.
- **A fat approval notification carrying the whole tag.** It would be a second,
  worse copy of the registry — stale between write and read. The notification
  carries identity and provenance only, and the engine reads the tag back, so an
  approval reversed between send and receipt does not still publish.
- **Failing the steward's approval when the listener is unreachable.** Rejected:
  it would make the registry's availability depend on an integration it does not
  own. `HttpApprovalNotifier` swallows transport failures — which is precisely
  why `SweepAsync` had to exist.
- **A `ProjectReference` from `RegLocationEngine` to `RegLocationProvider`.** The
  record shapes are duplicated instead, mirroring `EngEngine`/`EngProvider`. The
  duplication is the intended cost: it makes a breaking API change show up as a
  decision rather than a silent recompile.
- **Fabricating a deterministic UUID when `FederationGuid` is absent.** ENG does
  not mint federation identity — assigning it is an act of federation, not of
  design authoring. `IsPublishable` now drops unfederated elements instead, and
  the drain logs a warning naming the count. The stale comment claiming
  otherwise was removed from `EngModels.cs`.
- **Hashing the string `"ENG"` into `InfoSource/UUID`.** It looked stable but
  said nothing — every iModel produced the same value, so a receiver could not
  tell which model a segment came from. Now carries `IModelId`. See DR-018.
  `RegLocationSegmentsBuilder` avoids the same trap by deriving its `InfoSource`
  from `REG-LOCATION:{scopeId}` rather than the source name alone.
- **Removing the `uiApp` resource from `infra/sandbox/main.bicep` outright.** The
  template deploys Incremental, so deleting the block orphans a live Azure site
  rather than removing it. Left declared, with a `-DeleteLegacyUi` switch added
  to `deploy/sandbox/deploy.ps1` to retire it explicitly per environment.

## In-flight / known-broken

**The one thing missing:** nothing carries `SyncSegments` off the channel into
`RegLocationProvider`. `EngEngine` publishes to `oiie:sc01/ccom:SyncSegments`;
the only subscriber is the sandbox `SyncSegmentsHandler`, which writes
stewardship rows in the SimHost database, not into the provider's store. Until
an inbound consumer exists there is nothing for a steward to approve except tags
created by hand, and SC01 is half-wired. This is the next piece of work, not a
polish item.

Uncommitted in the working tree — all under `docs/PayItems/` (explicitly parked
as future work, ignore for now):

- `iModel-to-syncsegments-transformation.xslt` (untracked, ~500 lines). XSLT 1.0,
  transforms iTwin PayItem export into the grouped-PropertySet `SyncSegments`
  shape. Takes three inputs: payitems XML as context, plus `elementsUri` and
  `itwinUri` via `document()`. Not yet validated against `CCOM.xsd`.
- `GeneratedSyncSegmentsWithPayItems.xml` (untracked) — output of the above.
  Distinct from the committed, hand-built `SyncSegmentsWithPayItems.xml`. The two
  have not been diffed against each other.
- `ElementAspect EC Query.sql` (modified) — now joins `bis.Element` to recover
  the element class path, with `__x005C__`/`__x0020__`/`__x002D__` unescaped. The
  `WHERE` clause is still pinned to a single hardcoded element id
  (`0x70000000373`), so it is a probe, not a production query.

Known gaps elsewhere:

- **`RegLocationEngine` has never been run.** No Function app, no deploy script
  entry, no integration test crossing the provider boundary. The 10 new unit
  tests pin the BOD shape and the publish gate; everything else is unexercised.
- **The CIR category name is invented.** The engine writes entries under registry
  `{enterprise}` / category `FunctionalLocation`. Whether that matches what ENG
  registers on the ECSchema path is unverified — and if the two disagree the
  CIRIDs will not converge, which is the one thing the FederationGuid guideline
  exists to guarantee.
- **`GetApprovedTagsAsync` filters client-side.** It reads `tags` and keeps the
  approved ones in memory. Fine at demo scale, wrong at registry scale.
- **`EngPublicationService.DrainAsync` has no test coverage at all.** The publish
  leg — marker detection, watermark advance, session reuse, error-breaks-the-loop —
  is exercised by nothing. `RegLocationApprovalService` is in the same position.
- **Publication does not filter to the functional branch.** A tag corresponds to
  `Functional.FunctionalElement` and its descendants, but the drain filters only on
  `FederationGuid is not null`. Today every concrete class in `ENG_BOOTSTRAP.SQL`
  derives from `FunctionalComponentElement`, so the sets coincide by accident of
  seed data. Adding one physical class would publish geometry into REG-LOCATION.
- **`Oiie.Sandbox.Core.csproj` still has `RootNamespace` set to `SimHost`.**
  Cosmetic, but misleading now that the host is gone. The new tests sit in the
  `SimHost.Tests` namespace for the same reason.

## Environment
- Needs SQL Server LocalDB (`(localdb)\MSSQLLocalDB`). `EngHostFixture` creates a
  timestamped scratch database per run and drops it on dispose; a failed run can
  leave `EngE2E_*` databases behind, which is untidy but harmless.
- The E2E fixture starts the real `EngProvider` Functions host as a child process
  on a free port. It applies `ENG_BOOTSTRAP.SQL` itself *after* the host has come
  up healthy, because cold-start schema creation via `SchemaInitializer` is part
  of what the suite is testing.
- Seed GUIDs are read back from the API, never hardcoded — `IModelId` and
  `ConcreteClassId` come from `api/imodels` and `api/classes`.
- `local.settings.json` files are **committed**, not gitignored — the earlier
  claim in this document was wrong. They currently hold only local URLs and
  empty API-key placeholders, so nothing has leaked, but the next person to fill
  a key in will commit it. Either ignore them or move the keys to user secrets
  before that happens.
- `RegLocationEngine` needs `RegLocationBaseUrl`, `ScopeId`, ISBM channel
  settings, and — if `RegisterInCir` is on — `CirBaseUrl`. It also needs a blob
  container for its idempotency state, keyed by federation GUID plus revision.
  `GET engine/status` reports what it thinks it is configured with.
- The provider's `ApprovalNotificationUrl` must point at the engine's
  `POST engine/approved`. If it is unset, approval still succeeds and only the
  sweep will carry the tag onward — quietly. Worth checking first when an
  approval appears to vanish.

## Next
Build the inbound consumer: a subscriber on `oiie:sc01/ccom:SyncSegments` that
maps each segment into a REG-LOCATION tag in `Proposed` state, matching on
FederationGuid so a replayed BOD updates rather than duplicates. That closes the
loop, and only then can an SC01 end-to-end test assert the whole path: mint in
ENG → sweep into a named version → drain onto ISBM → land as proposed → approve
→ publish and register.

The PayItems transformation stays parked.

## Open questions — decide before implementing
1. Where does the inbound consumer live? Symmetry says a second entry point in
   `RegLocationEngine` — it already holds the provider client and the ISBM
   client, and the provider stays innocent of integration. The alternative is a
   separate project, which is more ceremony for the same result.
2. Does the SC01 test drive real hosts, or stub ISBM? Real hosts prove the most
   but make the suite slow and environment-dependent. The answer decides whether
   this extends `EngProvider.E2E.Tests` or needs its own project.
3. Should `CreateTagRequest.State` default to `Proposed` instead of `Approved`?
   Inverting it makes the safe case the default and forces the seed to declare
   its intent, at the cost of touching existing callers.
4. Should the functional-branch filter live in SQL (`vNamedVersionElement` joined
   to the class hierarchy) or in `IsPublishable` via `FullyQualifiedECClassName`?
   `EngElement` already carries the class name, so the engine-side check needs no
   schema change — but the SQL side would stop the rows ever being read.
5. What CIR category should a functional location register under, and does ENG
   agree? If the two sides disagree the CIRIDs will not converge.
6. Rule 4 remains open: nothing registers an ENG-IMODEL entry from the ECSchema
   path, so rule 8's "direct iModel navigation" claim does not yet hold.
